# AI Sandbox

AI Sandbox opens the native multi-agent workspace at `/#/ai-sandbox`.
Use the right-side **Quick start** menu to prepare a workspace, connect accounts, give AI a task, run the app, and connect its public address. The dashboard's main navigation stays on the left.

## Quick start

1. Select **New MicroVM**. The defaults are Ubuntu 26.04 LTS, 4 vCPU, 8 GiB RAM and a 16 GiB disk. If the microManager has 8 GiB RAM or less (the default on a 16 GiB Mac), choose 4 GiB in **Settings** or give the microManager more RAM ([microManager resources](micromanager-resources.md)). Select **Create workspace**; the coding AI is chosen later in **Connect accounts**. **Settings** lets you change resources, choose an internet-enabled MicroNetwork, or select a storage root before creation.
2. Firecrab downloads and installs the image when needed, reuses or creates an internet-enabled MicroNetwork, creates the reserved VM, starts it, and installs Git and GitHub CLI. Progress comes from the real jobs. The current stage shows its elapsed seconds, counted in the browser; a reload starts that count again from 0. Image/network/VM preparation is journaled in SQLite and resumes after a controller restart. Browser reloads follow the saved request ID; retries reuse the same VM reservation. A failed operation requires an explicit retry. An image can require a disk larger than the requested minimum.
3. **Connect accounts** shows GitHub AUTH and repository selection first, then the coding CLIs. Check one or more CLIs to install them, then sign in to each one. Tool installation and sign-in do not submit a model task. Existing regular VMs can also be selected and started from this page.
4. Use **AI tasks** to describe the app. Ask the agent to include tests and an app start command. Leave server startup to Firecrab. Tasks and terminals use the existing native VM runtime.
5. After coding finishes, open **Run app**. Review the detected commands, then choose **Verify and run**. Firecrab runs tests, the build and the app in order. It stops on failure. All coding tasks must finish before verification starts. Stop an already running owned app before another run.
6. **App address** can create a temporary public Quick Tunnel, or connect a fixed Firecrab address using a dashboard connection token. The fixed address points to the guest-owned Quick Tunnel rather than a reusable VM IP. The token stays in the privileged host store and is not saved in browser storage. Existing workspace addresses can be reconnected without re-entering their token.
7. Firecrab explicitly checks the app's HTTPS response. A new temporary address can take about a minute to work everywhere, so the check shows **Preparing the address** and retries for about 90 seconds. Only a successful response enables the embedded **Preview**. **Ask AI for another change** returns to the real task workspace. The public address stays on when you stop the app or run **Verify and run** again with the same port, so it keeps the same address; visitors see an error page while the app is stopped. **Stop public access** stops the guest's recorded preview connector. The address remains saved for later reconnection. Stopping/deleting the VM ends the guest tunnel; another VM cannot inherit the address through an IP reuse. To see the app without a public address, choose **View locally**: it opens the app at `http://127.0.0.1:<port>/` in a browser on the computer that runs Firecrab and in the embedded **Preview**. It needs no token. **Stop local access** ends it.

New workspace preparation requires image downloads and VM networking supported by the controller. Coding tools, terminals, verification and previews require the native management connection and a running VM. Unsupported or disconnected environments show their actual errors. No model output or app result is simulated. These controls create development previews; they do not commit, push, or publish a production release.

## Manage CLI agents in a MicroVM

The workspace runs coding CLIs inside the selected MicroVM. Project folders and login credentials stay in that VM. It does not accept a host project path or copy a host CLI account into the VM.

1. Select a regular MicroVM or create one with **Quick start**. New workspaces start automatically. Start or resume an existing stopped VM from **Connect accounts**. Internal service VMs cannot be selected.
2. Select **GitHub AUTH**. **Prepare GitHub AUTH** installs only the GitHub tools when needed; selecting or installing a coding CLI is not required. Copy the one-time code, open **Authorize on GitHub**, and approve **GitHub CLI** in the browser. The screen detects completion automatically. Pending requests survive browser/native-service restarts. An expired or denied request can be started again without an HTTP 409. The connection includes GitHub's `workflow` permission, which a push of GitHub Actions workflow files needs, together with GitHub CLI's default permissions. If the account was connected without it, the GitHub AUTH step shows **Add workflow permission**. It runs `gh auth refresh --hostname github.com --scopes workflow` in the VM and shows a new one-time code; the account keeps its other permissions. Fine-grained personal access tokens have no scopes, so Firecrab does not check them.
3. Choose a repository from the authenticated account, including private repositories, or enter `owner/repository`. Connect it once to this MicroVM. All new tasks and Web VS Code use `/workspace/firecrab/project`; new tasks do not clone again, reset local edits or switch branches. Use a different VM for another repository. An empty VM folder can also be initialized explicitly. Existing sessions keep their original folders.
4. Check **Codex**, **Claude Code**, **Grok Build** or any combination. **Install selected CLIs** installs Herdr and each checked CLI inside that VM. The VM installs one CLI at a time, so the others show **Waiting** until their turn; the installing CLI shows its elapsed seconds, and a failed CLI can be checked and installed again. Automatic installation supports Debian, Ubuntu and Alpine. Each installed CLI signs in separately: select **Connect Codex account**, **Connect Claude Code account** or **Connect Grok Build account** and finish its login terminal. Grok Build signs in with `grok login --device-auth`: open the link it shows on any device and enter the code. Firecrab never asks for or stores an API key. Grok Build counts as signed in when its session file `~/.grok/auth.json` exists; Firecrab checks only that the file exists and does not read it. Grok Build needs an xAI subscription that includes it, such as SuperGrok or X Premium+. Then enter the task and select **Start task**. GitHub AUTH and coding-provider authentication are separate. No model task runs during authentication.
5. If the CLI asks for first-run setup or project trust, finish that prompt in its terminal. **Send waiting task** then delivers the saved task explicitly. An uncertain delivery is shown for inspection instead of being replayed automatically.
6. Follow tasks in the default **Board** view. Cards show their coding CLI and move between **Waiting**, **Working**, **Needs attention**, and **Done** as the native runtime reports progress. Select a card to open its terminal. In **Terminals**, select up to four sessions in the side list. Click a terminal to type directly into that CLI. The **…** menu contains interruption, automation and session closure. Closing a session requires confirmation and retains its final output. No automatic commit, push or pull request is made.

**New task** lets you choose a connected Codex, Claude Code or Grok Build account for that task. Several tasks can run in parallel in the same VM workspace. A CLI session is created only when **Start task** is submitted. Opening the board, switching views and reloading do not launch or resend work. The view choice is saved per VM. Account login sessions stay outside the task board; CLI setup and uncertain task delivery remain visible for inspection.

The native localhost dashboard and `service dev` use the existing management connection to reach the selected VM. Each managed home and VM gets separate Firecrab session metadata and a private named [Herdr](https://herdr.dev/tui/docs/agents/) runtime. The bridge validates the controller, VM UUID, running state and pinned guest SSH key before connecting. It never falls back to a host coding CLI. A recycled terminal generation cannot receive input through an older session reference.

Browser reloads do not stop CLI sessions. Stopping the selected VM stops its CLIs. After the VM starts again, the next status refresh starts its Herdr runtime again and reconnects each open session in the same folder. Claude Code and Codex continue their saved conversation. Firecrab follows the conversation that each session's own CLI process uses, also after `/clear` or a new conversation that Claude Code starts by itself, and records it at most every 10 seconds. A resumed Claude Code session keeps its last permission mode, except bypass permissions. Firecrab starts Codex with `--no-daemon`, so each session keeps its own conversation and the board card shows its latest messages. Grok Build, and a session without a recorded conversation, for example one started before this version, start a new conversation; the session shows that. A waiting task is not sent again automatically, and a delivery that could not be confirmed stays marked for inspection. Sign-in and closed sessions are not started again. Preparing a CLI or closing a session does not start, stop or delete the VM. Files remain on the VM disk.

Installed GitHub Copilot commands can also be used. Automatic installation and sign-in controls cover Codex, Claude Code, Grok Build and GitHub CLI. Model overrides are supported for Codex, Claude Code and Grok Build; for Grok Build, choose **Other…** and type a model name. Reasoning effort choices are supported for Codex and Claude Code. Grok Build uses its own effort setting. The board shows no input or reply preview for Grok Build sessions. Provider usage can incur charges when the user starts work.

Installation and authentication follow the official [Codex CLI](https://learn.chatgpt.com/docs/codex/cli), [headless Codex authentication](https://learn.chatgpt.com/docs/auth#login-on-headless-devices), [Claude Code setup](https://code.claude.com/docs/en/setup), [Grok Build](https://docs.x.ai/build/overview) and its [CLI reference](https://docs.x.ai/build/cli/reference) and [Herdr installation](https://herdr.dev/tui/docs/install/) instructions.

## CODE VS Code links

The **CODE → VS Code** page (`/#/code`) lists the projects linked in AI Sandbox. It is read-only: link repositories and manage tasks in AI Sandbox.

- Each card is one running regular MicroVM with a linked repository. It shows the repository, branch, project state and MicroVM name.
- Each open agent session gets one **Open VS Code** link. It opens the same AI Sandbox editor in a new tab. Sign-in and closed sessions get no link.
- A project that is still preparing shows no link. The page checks it again every 5 seconds.
- **Open in AI Sandbox** selects that MicroVM on the AI Sandbox page.
- Stopped MicroVMs are not checked. The page shows how many it skipped.

The links need the microManager connection of the main server dashboard at `http://127.0.0.1:5523/`:

| Host | Behavior |
| --- | --- |
| macOS | Supported. If the page cannot reach the host, run `firecrab service status` and `firecrab service start` in Terminal. |
| Windows | Supported. If the page cannot reach the host, run `firecrab service status` and `firecrab service start` in PowerShell. |
| Linux | Not supported yet. Linux runs the main server natively, without microManager. Check the server with `systemctl status firecrab-helper firecrab-api`. |

CODE workspaces from v0.4.3 were removed. Their MicroVMs stay in the MicroVM list as regular MicroVMs, and their saved records are no longer read.

## Verification, GitHub Actions and tunnel previews

Open a coding session's **… → Automation and preview** menu.

1. Review **Execution settings**. Commands run in that task's existing MicroVM workspace. Install the project's runtime/toolchain in the VM first. Test commands must finish; `CI=true` disables watch mode in tools that support it. The optional test app must stay in the foreground and listen on `127.0.0.1` or `0.0.0.0` at the selected port.
2. **Run verification** runs tests, the optional build and the optional test app in that order. A failure stops the sequence.
3. The job runs inside the VM with a workspace lock. Browser/native-server restarts do not restart it. A VM reboot interrupts it. Results and bounded displayed logs remain available. Stop the owned test app before another run; other processes are never stopped by PID alone.
4. **Create workflow** creates `.github/workflows/firecrab-checks.yml` in the VM. It runs the configured tests and build on pushes, pull requests and manual dispatch. It uses a pinned checkout action and read-only repository permissions. Existing files are not overwritten. Inspect and push the changes separately; creation does not publish a commit, PR or production deployment.
5. **Load workflow runs** reads recent GitHub Actions runs through the GitHub account connected inside the VM. Each run shows its branch, commit and result. This is separate from the local verification result.
6. After verification passes and the app is ready, **Create test URL** starts a dedicated Cloudflare Quick Tunnel inside the selected VM. The first use downloads the official connector and verifies its GitHub-published SHA-256 digest. The temporary HTTPS address is public. Firecrab shows it only after the connector registers its connection. Browser/native-server restarts find the same recorded process. The tunnel belongs to the VM workspace, not to one run: a later run with the same app port uses the same tunnel and address. A new app port stops it, and the next connect starts a new one. Stopping or deleting the VM ends the connection; an IP address reused by another VM cannot inherit it. Existing Pipe routes and tunnels are untouched.
7. **Check HTTPS** makes an explicit external request to this task's recorded Quick Tunnel origin. It displays the HTTP status and response time without following redirects. A new address can be missing from DNS for its first minute, so connect, DNS and timeout errors are retried for about 90 seconds; any HTTP response ends the wait. A connector's running state alone is not proof that public HTTPS works, and a kept tunnel needs a new check after each run. **Stop public access** stops that connector. **Stop test app** stops only the recorded app process group after checking its boot and process start identity; public access stays on, and visitors see an error page until the app runs again. A stopped tunnel can be started again while the verified app remains running.
8. **View locally** shows the app on the computer that runs Firecrab, with nothing published to the internet. Firecrab keeps one SSH loopback forward to the VM, `127.0.0.1:<host port>` to the app's `127.0.0.1:<port>`, so apps that listen on `127.0.0.1` or `0.0.0.0` both work. The host port is the app's port when nothing on the computer uses it, else a free port. Ports that the Firecrab dashboard and its API use are never chosen. Firecrab then checks `http://127.0.0.1:<host port>/` once; any HTTP status means the app answers. The address opens only in a browser on that computer. This check does not count as the HTTPS check for **Connect Firecrab address**. **Stop local access**, **Stop test app**, a new app port, a VM stop and an exit of the native Firecrab service end the forward. After a service restart, choose **View locally** again.

This provides test-environment deployment. Production release targets, credentials and approval rules must be configured separately. No production deployment is performed automatically.

## Control an agent terminal

Click the task's terminal to type directly into its existing CLI session. Enter, Tab, arrow keys, Ctrl+C and paste go to that terminal. There is no separate reply box or send button. Resize the pane to resize its PTY. Scroll inside the terminal to read its history; hold Shift to select text when the CLI uses the mouse.

Closing a browser tab or deselecting a task releases terminal control without stopping the agent. **Reconnect terminal** attaches to the same session. Input is never replayed after a disconnect. A session controlled by another client is not taken over automatically. **End session** explicitly stops its CLI. Completed sessions retain read-only output. Verification blocks new terminal input while its workspace is being checked.

## Edit task files with Web VS Code

1. Select a coding task and choose **Web VS Code** beside its workspace path.
2. On first use, Firecrab installs the official OpenVSCode Server inside that MicroVM. The connection page shows installation progress.
3. The editor opens `/workspace/firecrab/project`, the same VM folder used by every new CLI task. Existing sessions retain `/workspace/firecrab/TASK_UUID`. Saving edits changes those files directly. Guest-side changes appear in the editor too.
4. Reopening the editor reuses its recorded server and private SSH connection. It does not create another project or copy files to the desktop.

The editor uses a token-protected guest loopback listener and a pinned SSH loopback forward. It does not publish a test tunnel. Workspace Trust prompts remain enabled. Login sessions do not expose an editor button.
